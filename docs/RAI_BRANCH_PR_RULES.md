# RAI_BRANCH_PR_RULES.md v0.3 (GitHub 브랜치 및 PR 운영 규칙)

본 문서는 스프린트 2(S2) UX/UI 병렬 개발 진입에 앞서, 개발자 덱스(Dex)가 GitHub 형상 관리 프로세스를 일관되게 운영할 수 있도록 브랜치 전략, Pull Request(PR) 작성 규칙, QA 체크 기준, merge 기준, 예외 상황 처리 방법을 정리한 깃 운영 기준서입니다.

> [!WARNING]
> **주의**: 본 문서는 S2 진입 전 GitHub 운영 규칙을 정리하는 기획 계획서입니다. 본 단계에서 실제 GitHub 브랜치 생성, PR 생성, merge, 앱 코드 작성 등 개발 구현 실행은 수행하지 않습니다.

---

## 1. 문서 목적
* **S2 GitHub 운영 기준**: S2 단계에서 덱스가 여러 기능 브랜치로 나누어 작업을 진행할 때 일어날 수 있는 코드 충돌을 예방하고, 이관 품질을 확보합니다.
* **덱스 작업 브랜치/PR 규칙**: 덱스가 작업을 마친 뒤 main 브랜치로 병합하기 위해 작성해야 할 PR 요구사항과 증빙 기준을 명문화합니다.
* **운영 규칙 설계 단계 명시**: 본 문서는 실제 형상관리를 실행하기 전 덱스 개발 계약의 일환으로 규칙을 설계 및 정의하는 사전 기획용 문서입니다.

---

## 2. 브랜치 명명 규칙
* **main 브랜치 직접 push 제한**: main 브랜치 직접 push는 진행하지 않으며, 모든 코드는 Pull Request 검수 프로세스를 거쳐 병합됩니다.
* **S2 UX/UI 개발 기능 브랜치 예시**:
  * 디자인 토큰 및 공통 레이아웃: `feature/s2-ux01-token`
  * 랜딩 및 submit 입력 폼: `feature/s2-ux02-landing-submit`
  * 리포트 화면 시각 계층: `feature/s2-ux03-report`
  * 모바일 탭/반응형 검수: `feature/s2-ux04-mobile`
  * 브라우저 인쇄 레이아웃: `feature/s2-ux05-print`
* **브랜치 생성 유예**: 본 ST10 기획 설계 단계에서는 실제 GitHub 브랜치 생성을 실행하지 않고 깃 가이드라인 수립으로 한계를 둡니다.

---

## 3. PR 작성 기준 및 6대 증빙
덱스는 승인된 S2 기능 브랜치 작업 후 main 브랜치 병합 요청용 PR을 작성할 때, 변경 내용의 정상 동작을 확인할 수 있도록 아래 6대 증빙을 PR 설명 본문에 포함합니다.

1. **로컬 구동 URL**: 덱스 로컬 환경에서 개발 서버가 구동 중인 로컬 URL 정보 (예: `http://localhost:5173/`).
2. **모바일 375px/390px 캡처**: 반응형 검수를 통과했음을 보여주는 모바일 SE(375px) 및 표준(390px) 뷰포트 크기의 캡처 이미지.
3. **0건/1건/100건/101건 테스트 결과**: CSV 입력란 경계값(데이터 없음, 1건, 100건, 101건 초과 모달 노출) 조작 시의 파싱 결과 로그 또는 피드백 팝업 캡처.
4. **금지 표현 grep 결과**: 소스 코드 내에 금지 단어가 노출되지 않음을 증명하는 grep 터미널 검색 결과.
5. **인쇄 미리보기 캡처**: 브라우저 인쇄 모드(Cmd+P)를 트리거했을 때 불필요한 UI가 정상적으로 제외되고 화이트 배경으로 처리된 A4 규격 출력 미리보기 캡처.
6. **최종 수정 파일 목록**: 본 태스크 범위 내에서 수정한 HTML, CSS, JS 파일 목록 요약.

## 4. PR 템플릿 마크다운 예시
덱스는 main 브랜치로 풀리퀘스트를 작성할 때 아래 템플릿을 복사하여 사용합니다.

```markdown
## 1. 관련 백로그 ID
* 백로그: [RAI-S2-UX0X] (태스크명 입력)

## 2. 작업 목적
* (예: 수동 리뷰 CSV 파일 드롭존 피드백 및 파싱 피드백 컴포넌트 마크업)

## 3. 수정 파일 목록
* `product/index.html` (수정 부분 요약)
* `product/index.css` (수정 부분 요약)

## 4. PR 제출 6대 증빙
- [ ] 1. 로컬 구동 URL: (예: http://localhost:5173/)
- [ ] 2. 모바일 반응형 캡처: (iPhone SE 375px 및 390px 스크린샷 링크/이미지 첨부)
- [ ] 3. CSV 용량 경계값 테스트 결과: (0건, 1건, 100건, 101건 초과 모달 팝업 콘솔 로그 또는 캡처)
- [ ] 4. 금지 표현 grep 검색 결과: (grep 명령어 구동 결과 매칭 0건 텍스트 첨부)
- [ ] 5. 인쇄 미리보기 캡처: (Cmd+P 출력 미리보기 화면 캡처 첨부)
- [ ] 6. 최종 수정 파일 요약: (수정된 마크업/스타일 시트 파일 요약 첨부)

## 5. 완료 기준(Acceptance Criteria) 자가 체크리스트
- [ ] 기획서에 정의된 시퀀스 및 레이아웃 배치 순서가 일치하는가?
- [ ] 터치 인터랙티브 영역의 크기가 가로/세로 44px 이상 확보되었는가?
- [ ] 임의로 PG사 결제창이나 크롤링 UI를 설계/추가하지 않았는가?
- [ ] 민감어 감지 주황색 배지가 리포트 지표와 격리되어 카드 내부에 올바르게 렌더링되는가?
```

## 5. merge 승인 기준
* **빌 (QA/검수 리드) 검토**: 덱스의 PR 본문에 6대 증빙이 모두 수록되었는지 대조하고, 기획서 QA ID(`QA-HM`, `QA-IP`, `QA-RP`, `QA-MB`, `QA-PR` 등 총 29대 항목)와의 일치 여부를 검토하여 승인 가능 여부를 확인합니다.
* **라이언 (기획 리드 PO) 확인**: 화면 구성의 신뢰성, 상품 가치 전달 완성도, 마케팅 문구의 어조 및 AI 답글의 톤 전환 완성도를 검토하여 최종 Done 승인 여부를 결정합니다.
* **병합 규칙**: 빌과 라이언 PO 양자 모두의 확인 및 승인 의견이 PR에 등록되기 전에는 main 브랜치로의 merge 진행은 하지 않습니다.

---

## 6. Blocked 에스컬레이션 3단계
개발 도중 기술적 장애물이나 기획적 마찰로 진행이 지연될 경우, 덱스는 독단적으로 수정을 강행하지 않고 아래 3단계 규칙에 따라 대응합니다.
1. **1단계 (Blocked 상태 전환)**: 해당 백로그의 스크럼 상태를 `Blocked`로 신속히 변경합니다.
2. **2단계 (차단 사유 기록)**: 백로그 설명 칸에 현재 직면한 병목 원인(기술 제약, 비용 소모, 데이터 구조 충돌 등)과 대체 가능한 2~3종의 우회 옵션을 구체적으로 작성합니다.
3. **3단계 (의사결정 대기 후 재개)**: 빌의 사업성 평가 및 라이언 PO의 최종 기획 결정이 완료되어 승인될 때까지 해당 기능 개발을 중단하고 대기합니다.

## 7. 금지 사항
개발자 덱스는 아래 항목 중 하나라도 위반하는 행위를 피해야 하며, 위배 시 인수 거부 및 재작업 지시가 내려집니다.
* **실행 행위 제한**: 본 ST10 문서 정리 단계에서는 실제 앱 동작 코드 작성, 베이스라인 외 scaffold 생성, 실제 기능 브랜치 생성, 실제 PR 작성, main merge 실행을 진행하지 않습니다. S2 공식 개발 단계에서는 승인된 브랜치/PR 운영 규칙에 따라 작업합니다.
* **오프 스코프 기능 구현 금지**:
  - 스토어 API 연동 자동 리뷰 수집 UI 추가 금지.
  - PDF 자동 변환 및 파일 다운로드 UI 추가 금지.
  - 가짜 또는 실제 결제 완료 화면 추가 금지.
  - 사장님 복사 전 자동 답변 게시 UI 추가 금지.

## 8. 금지 표현 검색 기준 (Grep Rules)
덱스는 풀리퀘스트 발급 전, 작업한 소스 코드 전체를 대상으로 아래 정규식/단어 검색을 실행하여 검출 건수가 0건이 되도록 정제해야 합니다.
* **코드 내 금지 단어 검색 대상**:
  - `허위 리뷰`: 위험 우려 리뷰 감지 등으로 표현 완화할 것.
  - `악성 고객` / `블랙컨슈머`: 별점 및 불만 빈도 기준 우려 리뷰 등으로 순화할 것.
  - `리뷰 삭제 보장`: "보장" 표현 사용 금지.
  - `매출 상승 보장`: "보장" 표현 사용 금지.
  - `검색 노출 보장`: "보장" 표현 사용 금지.
  - `100%`: 100% 만족 등의 과장형 수치 표현 사용 금지.
  - `완벽` / `최상` / `전격`: 극단적이거나 단정적인 어구 사용 금지.
* **Grep 검색 권장 명령어 예시**:
  ```bash
  grep -rnI -E "허위 리뷰|악성 고객|블랙컨슈머|삭제 보장|상승 보장|노출 보장|100%|완벽|최상|전격" ./product
  ```
